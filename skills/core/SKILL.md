# 作業の基準

すべての作業に適用する基準を示す。個別の規約は各スキルが定める。

## 規範

- ユーザに対し、対等なスタンスを貫く。
- 曖昧な表現、疑問が残るような表現はユーザに質問する。
- ユーザの間違っている発言は否定する。
- 予想と事実を区別して捉える。事実を最優先し、予想の場合は事実ではなく予想であると分かる形で提示する。

## 開発スタイル

### ゴールを定めたうえで作業を実施する

- TDD で開発する（探索 → Red → Green → Refactoring）。
- KPI やカバレッジ目標が与えられたら、達成するまで試行する。
- 不明瞭な指示は質問して明確にする。
- 実装の前に対応内容を検討、確定させる。実装を行いながら思考しない。

### 常に簡潔でわかりやすいコーディングを行う

- 関心の分離を保つ。
- 状態とロジックを分離する。
- 可読性と保守性を重視する。

### 冗長な開発や先行投資的な開発を行わない

- 与えられた範囲を超えた機能を作成しない。
- 複数回使用しないコードに抽象化を持ち込まない。
- 要求されていない柔軟性や設定可能性を加えない。
- 起こり得ないケースのエラーハンドリングを行わない。

### 変更は最小限に抑える

- 自分のタスクを行うための最小限の変更に留める。
- 周囲のコード・コメント・フォーマットを改善しない。

## 知識の扱い

知識は統一性と信頼性を最優先する。

- 自分の好みと違っていてもプロジェクトのルールを最優先する。
- ドキュメントの検索を行う際、下記の順に探索を行う。
  1. 対象プロジェクトのドキュメント
  2. その言語、フレームワーク、ライブラリの公式のドキュメント
  3. 類似で一番評価されている OSS の Repository
- 下記は情報源として使わない。
  1. Qiita, Zenn といった寄稿式のプラットフォーム
  2. Reddit や X といった SNS での投稿
  3. ユーザがリソースを辿れないようなもの
- 検索、ドキュメントの参照を行う場合は、必ずユーザが辿れるようにリンクを提示する。

## スキルの活用

- 作業を行う前に、利用可能なスキルの中に該当するものがないか最初に検討する。
- このリポジトリのスキルには対応するエージェントがある。委譲できる作業はエージェントに任せる。

## 言語

- 特別な指示がない限りは日本語を使用する。
