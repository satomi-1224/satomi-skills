# コメント規約

コメントを書くときの分量、形式、アノテーションの使い分けを示す。

## 原則

- **何をしているかはコードで示す。** コメントには読んでもわからないことだけ書く。
- 消しても情報が失われないコメントは書かない。
- コードを変えたらコメントも直す。追随できないコメントは残さない。

## 分量

- 長い文章的なコメントを書かない。1 コメント 1 主題、原則 1〜2 行に収める。
- 段落単位の解説はコメントの担当ではない。README や `docs/` に置き、コメントからは参照だけする。
- 説明が長くなるのはコードが複雑なせいであることが多い。書き足す前に、分割と命名で解けないか見る。

## 形式

適用の優先順位。上が強い。

1. リポジトリの規約（`CLAUDE.md`、`CONTRIBUTING.md`、lint / formatter の設定）
2. その言語・フレームワークの公式スタイルガイド
3. 周囲の既存コード

**自分の好みで形式を選ばない。** 迷ったら同じファイルの既存コメントに合わせる。

- 区切り線や `=====` の見出しなど、独自の装飾を作らない。

## 書かないコメント

| 例 | 理由 |
|---|---|
| `// ユーザーを取得する` の直後に `getUser()` | 関数名と同じ。ソースを読めばわかる |
| `count++ // count を 1 増やす` | 言語仕様の説明 |
| コメントアウトしたコード | 履歴は git が持つ。消す |
| 作者・更新日・変更履歴 | git blame が持つ |
| 空欄が並んだ自動生成テンプレート | 情報がない |

## 書くコメント

- 直感に反する実装の理由。「なぜこの順序か」「なぜこの値か」
- 外部要因による回避策。issue / PR / 仕様書へのリンクを添える
- 呼び出し側が守る前提条件、仕様上の制約
- 意図的に何もしていない箇所（空の catch、早期 return）
- 正規表現や計算式の意味

## アノテーション

`TAG: 内容` の形で書く。タグは大文字、直後にコロン。

| タグ | 用途 |
|---|---|
| `TODO:` | これから足す作業 |
| `FIXME:` | 動いているが正しくない箇所 |
| `NOTE:` | 知らないと誤解する補足 |
| `HACK:` | 妥当でない手段を意図的に選んだ箇所。正攻法を採らなかった理由を書く |
| `WARNING:` | 触ると壊れる箇所。どう壊れるかを書く |

- 表に無いタグ（`XXX:` `OPTIMIZE:` `REVIEW:` など）は使わない。
- 追跡先があるものは番号か URL を添える（`TODO(#123): ...`）。
- `TODO:` と `FIXME:` を混同しない。未実装は `TODO:`、正しくない挙動は `FIXME:`。
- 今すぐ直せるものに `TODO:` を書かない。直す。
- 解除条件を書く。いつ消せるかわからない `TODO:` は残さない。

## コメントの言語

- 日本語で書く。既存コードが英語で書かれている場合は英語に合わせる。
- 識別子、API 名、エラーメッセージは原文のまま書く。訳さない。

## やらないこと

- 読みにくいコードをコメントで補う。コードを直す。(直したうえで複雑なものは補足としてコメントする)
- 依頼されていない箇所へドキュメンテーションコメントを一括で付ける。
- lint / formatter が管理している書式を手で崩す。
- 1 つのファイルの中で日本語と英語のコメントを混在させる。
- 一切触っていない箇所のコメントアウトの修正を行う。（明示的に依頼したときは修正を行う）
